复查日期：2026-10-02。依据当前源码、课程要求对照和上一轮验收记录。本次进行了静态复查、现有检查重跑，以及临时库中的新增并发反例验证；没有修改业务实现或正式数据库。

## 当前判断

项目已经形成可演示、可本地试用的零售销售分析工作空间：四表导入、质量校验、不可变版本、授权看板、分析任务、证据、审核修订、导出和建议反馈能够贯通。多人远程使用和真实模型效果还需要实际环境验收；本次新发现的账号并发写入问题应优先修复。

- 本次重新执行 `npm run check`：67 项后端测试、4 项前端辅助测试、生产构建、Ruff 和 Prettier 均通过。
- 本次新增反例：重置密码与禁用/撤销门店授权交错进行，会使已禁用账号重新启用并恢复原门店。现有测试未覆盖这一交错场景。
- 上一轮浏览器完整流程 1/1、冻结题 30/30 通过；本次未重跑浏览器或完整性能测量。
- 上一轮 10 万条明细的冷看板 P95 约 0.296 秒，是进程内测试。测试进程峰值约 850 MiB 包含数据生成和请求编码，不能直接等同于正式服务内存。

上述结果应一起理解：现有测试通过与新增反例失败并不矛盾，需要把反例纳入回归。已有指标、权限和历史证据验收仍是有效的开发基础，不能据此宣称所有并发行为已正确。

## 优先修复：账号并发更新

**确认的问题。** `backend/app.py:765` 在密码计算前读取整个账号，随后等待后台密码计算，最后在事务中把该旧账号整体写回。期间发生的禁用、角色或门店变更会被覆盖。`update_user` 同样在事务外读取整个账号；多进程下还存在反向覆盖密码变更的风险，该反向场景本次未单独复现。

本次使用实际 FastAPI 接口和临时 SQLite 库，在密码计算处设置同步点，得到：

| 时点 | enabled | stores |
| --- | --- | --- |
| 初始账号 | true | `["SH01"]` |
| 禁用并撤销门店接口返回 200 后 | false | `[]` |
| 较早启动的重置密码接口返回 200 后 | true | `["SH01"]` |

建议在密码计算后进入事务，重新读取当前账号及操作者授权，只修改该操作负责的字段。账号状态、凭据与会话撤销应一致提交；有冲突的编辑可采用版本号检测。不要仅给旧对象写回加锁，这不能消除旧值覆盖。

验收应覆盖重置与禁用、重置与撤销授权、重置与自助改密、两个管理员并发编辑，以及跨服务进程操作。最终禁用状态和撤销范围不能被密码操作恢复，密码操作不能被角色编辑覆盖。
