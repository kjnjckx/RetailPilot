# RetailPilot 优化评审与开发清单

评审日期：2026-10-01。范围：当前源码、README、PRD、实现记录和本地验证。

本文保留优化前的评审依据。第二、三批与目标阶段的当前实现及边界见 [后续批次验收](batch2-3-acceptance-2026-10-02.md)。第一批 OPT-01～04 已实施，最新行为与验证结果见 [第一批实现与验收](batch1-acceptance-2026-10-01.md)。

## 1. 总体判断

项目已经具备本地零售分析工作台的完整业务流程：账号与门店授权、CSV 校验、事务发布不可变快照、看板、规则分析、证据、报告审核、修订和反馈。金额以整数分存储、取消订单排除、空数据与零值区分、历史快照稳定等设计应继续保留。

当前最值得投入的是问题理解与结果正确性、角色权限一致性，以及可复现的验收。增加分析能力前，应先保证系统不会把不支持的问题解释成另一个问题。

以下 P0/P1/P2 是本次建议的修复顺序，不替代 PRD 原有的需求分级：

- P0：优先解决，影响答案或权限正确性。
- P1：下一轮完善，影响可靠性、使用体验和课程验收。
- P2：按规模或部署需求推进。

## 3. P0：优先修复的正确性问题

### OPT-01：让比较结果真正对应用户所问指标

**证据：** `backend/domain.py:265` 的问题规划只检查是否出现“销售、订单、客单价、销量”，返回的计划没有指标字段；`backend/domain.py:368` 的变化额、变化率与异常规则固定使用净销售额。分析页面的核心比较卡片也固定展示销售金额，见 `src/pages/Analysis.tsx:314`。

**已复现：** 对测试夹具提问“2026 年 8 月订单数相比 7 月变化多少？”，两期订单均为 496 笔，实际变化为 0；系统摘要却强调销售额下降 8,000 元、下降 4.44%。问客单价变化也返回同一套销售额比较。

**建议：** 在分析计划中记录指标、单位和比较方式；按指标计算差额、变化率与排名，并让图表、摘要和报告使用同一结果契约。多指标问题明确返回多个指标结果。客单价应由销售额和有效订单数计算，不能把各门店客单价直接相加。

**验收：** 四个支持指标分别验证本期值、基期值、变化额和变化率；覆盖多个指标、零基期、空基期和排名问题。订单数不能出现人民币单位。

### OPT-02：不支持的时间和范围必须明确澄清

**证据：** `backend/domain.py:298` 默认基期为上月；`backend/domain.py:322` 用 `next(...)` 取第一个匹配地区。

**已复现：**

- “2026 年 8 月净销售额同比变化多少？”被执行为 8 月与 7 月比较。
- “2026 年 8 月华东和华南净销售额”只计算华东，返回 80,000 元；测试数据中两地区合计为 172,000 元。

**建议：** 显式识别同比、环比、多个地区及范围冲突。暂不支持的组合进入澄清状态；执行前展示指标、本期、基期和门店范围。解析器与后续模型适配层共同遵守这一规则。

**验收：** 上述两题不能静默执行错误计划；缺去年数据的同比问题明确提示覆盖不足；多地区问题要么正确合并，要么明确拒绝当前不支持的组合。

### OPT-03：读取数据也要同时检查业务角色和门店范围

**证据：** `backend/app.py:249` 的看板入口检查登录和门店范围，但没有业务角色检查。任务列表、任务详情和部分报告读取路径也需要统一审查。PRD 第 4 节要求角色与门店授权同时满足。

**已复现：** 临时数据库中给仅有 `admin` 角色的账号配置 `SH01` 范围，不添加分析、管理或门店角色，即可读取看板，接口返回 200。

**建议：** 定义统一的“读取经营数据”权限，应用于看板、版本元数据、任务、报告与导出；明确管理员的导入校验职责与经营读取职责。权限变更后再次检查历史对象和运行任务所需角色。

**验收：** 仅管理员、管理员兼业务角色、分析人员、管理人员和门店人员组成角色矩阵；对列表、详情、执行和下载分别验证。撤销业务角色但保留门店范围也应及时生效。

### OPT-04：历史报告导出固定使用当时的指标版本

**证据：** `backend/app.py:732` 导出写入的是当前全局 `METRIC_VERSION`，虽然任务与证据保存了生成时的指标版本。

**影响：** 当前只有 `sales-v1`，暂未发生版本漂移；未来修改指标版本后，旧结果可能被标成新口径。这是源码确认的后续风险，尚未复现真实版本升级。

**建议：** 报告创建时保存指标版本，导出读取报告或证据内的固定版本；检查版本、范围与证据之间的一致性。原始数据版本不可用时应阻止正式导出，而不是只在正文提示。

**验收：** 创建旧报告后升级指标定义，旧报告的数值、公式说明和版本标签仍保持一致。

## 4. P1：可靠性与开发质量

### OPT-05：统一输入校验与导入错误提示

**已复现：** 150,000 字符的单个 CSV 字段使导入接口返回 500，尽管文件远低于批次 20 MB 限制。原因是 CSV 解析异常没有转成可读的业务错误。另有 `version_id: []` 被当成未指定版本并返回 200，说明请求类型约束不完整。

**建议：** 为任务、发布、账号和报告操作定义明确的请求模型，校验类型、长度和枚举；捕获 CSV 解析异常，给出表、字段或可定位的行信息。前端字段映射目前直接按逗号拆表头，见 `src/pages/DataCenter.tsx:332`，应采用支持引号和转义的解析方式。前端同时检查四个文件的合计大小。

**验收：** 非法类型、超长字段、引号字段、BOM、空文件与编码异常均有可操作提示；用户可修正的输入不返回通用 500。请求模型的框架用法参考 [FastAPI 官方文档](https://fastapi.tiangolo.com/tutorial/body/)。

### OPT-06：明确重复检测的含义

**证据与复现：** `backend/domain.py:166` 对包含数组顺序与 `_row` 的解析数据计算指纹。四表业务记录不变，仅倒序排列数据行，指纹即改变，不能识别为同一业务快照。

**建议：** 区分原始文件指纹与业务内容指纹。业务指纹按稳定主键排序，排除行号等导入元信息，保留所有影响计算的字段；原始行号继续用于问题定位。明确相同交易但不同覆盖声明或快照时点应如何处理。

**验收：** 相同业务记录重排可识别为相同内容；金额、退款或商品归类真正变化时识别为新内容。

### OPT-07：用真实阶段工作驱动任务进度

**证据：** `backend/app.py:447` 每阶段固定等待 0.45 秒；完整分析在“查询”阶段完成，“统计分析”和“报告编制”主要取出已有结果。当前是有结构化记录的规则流程，尚未实现模型驱动的多智能体协作。

**建议：** 将规划、查询、统计、核验、编制拆成实际职责，记录开始、结束、耗时与错误；移除展示性等待。为任务增加持久化排队、执行上限、取消和失败分类。当前“最多两个任务”应展示排队或繁忙原因。

**验收：** 阶段时间反映实际处理；取消后不再开始新阶段；重启后任务进入可解释的终态；失败能够定位到阶段。数据库锁与任务状态更新策略在多进程部署前单独验证，当前进程内锁不提供跨进程保证。

### OPT-08：补齐验收集、前端流程测试与持续检查

**现状：** 26 项自动化测试重点覆盖后端。PRD 要求冻结 30 道分析题并达到至少 27/30，目前未见该评估集；新增复现问题也没有进入现有回归用例。

**建议：** 将 OPT-01～06 的反例加入有预期结果的回归集。冻结基础聚合、趋势比较、维度拆解与异常报告问题，另设歧义、越权和失败集合。浏览器流程覆盖首次创建管理员后的空状态、导入发布、分析澄清、审核修订、退出及过期会话。建立每次变更执行构建、业务测试和静态检查的流程。

**验收：** 每题有正确指标、时间、范围和数值；不能只判断接口是否返回成功。拒答规则单独评价。构建通过与业务验收通过分别记录。

### OPT-09：让前后端共享明确的数据结构

**证据：** `src/lib.ts:1` 使用 `Record<string, any>`，任务、证据、报告和版本依赖页面约定字段；`backend/app.py` 已有 888 行，接口、授权、任务执行和导出集中在一起。

**建议：** 为用户、版本、任务状态、指标结果、证据与报告定义具体类型；后端按认证、导入、分析、报告和审计划分模块，业务状态转换集中管理。优先稳定分析结果契约，再做模块拆分。

**验收：** 指标单位、结果字段或状态变化能在开发阶段被发现；各模块继续调用同一授权和指标计算逻辑。

## 5. P1：使用体验与课程材料

### OPT-10：减少首次使用和跨页面操作的阻力

**源码依据：** `src/App.tsx` 用内存中的 `page` 切换页面，没有 URL 对应页面和任务；`src/pages/Settings.tsx` 用文本填写门店 ID；`src/pages/Dashboard.tsx:407` 的深入分析入口使用版本最新完整月，而非当前筛选日期。

**建议：**

- 增加“创建账号 → 导入数据 → 配置门店授权 → 首次分析”的进度引导，让空状态提供对应下一步。
- 门店选择显示名称和 ID，未导入门店允许手工配置但显式标记待确认。
- 看板转分析时带上当前门店和时间；当前范围不适合自然月分析时明确说明并让用户调整。
- 页面、任务和报告支持可恢复的 URL，刷新与浏览器返回保留上下文。
- 按角色展示可执行入口，并保留清楚的无权限说明。
- 分析轮询避免旧任务响应覆盖新选择；报告关闭前提示未保存修改。
- 显示完整年份与明确时区；当前 `src/lib.ts:11` 的时间格式依赖浏览器时区且省略年份。

**验收：** 新用户可从空库完成第一份报告；从看板进入分析不会悄悄更换时间范围；页面刷新后能够定位原任务。

### OPT-11：同步实际能力与课程验收文档

**证据：** README 已说明空库启动和真实数据导入；`docs/implementation-v0.1.md` 仍记录预置公开演示账号及 25 项测试。PRD 的多智能体目标与当前规则流程之间也有明确差距。

**建议：** 保留历史记录并标注已过时内容，补充当前版本验收记录。维护“需求编号 → 实现状态 → 证据 → 未完成项”的表。课程展示分别解释已实现规则流程、计划中的模型角色和量化评估，不将阶段名称当作多智能体达标证据。

**验收：** 首次安装说明、演示说明、测试数量和能力边界一致；每项课程承诺能对应代码、测试或明确的待实现项。

## 6. P2：数据规模、智能化与部署

### OPT-12：先量化性能，再调整存储和查询

**源码依据：** `backend/storage.py:59` 读取某类全部 JSON 对象；`backend/app.py:120` 即使指定版本也先加载全部版本；版本列表计算授权行数时遍历订单与明细；任务和报告列表返回完整结果与证据。`backend/domain.py:186` 每次聚合遍历交易数据。

同步 SQLite 操作、密码计算、CSV 校验和统计在异步接口中直接执行，存在阻塞其他请求的风险。处理方式应依据测量结果决定，异步执行原则可参考 [FastAPI 官方文档](https://fastapi.tiangolo.com/async/)。

**建议顺序：**

1. 使用独立生成数据测量 1 万、10 万条明细，以及多个历史版本下的延迟、内存与响应大小。
2. 指定版本直接按 ID 取；列表只返回摘要、分页和服务端筛选，详情再取证据。
3. 将版本元数据与交易数据分离；需要时引入版本化关系表，建立版本、日期与门店索引。
4. 对不可变版本的授权聚合结果做缓存，键包含数据版本、指标版本、范围和筛选条件。
5. 将耗时工作移出事件循环，验证同时导入、登录、读取和分析时的响应。

**验收：** 对照 PRD 的 10 万条明细、至少 50 次测量和常用请求 P95 ≤ 3 秒目标；记录环境、冷/热缓存和失败率。此次只有静态风险分析，没有压测结果，不宣称已经超出性能目标。

### OPT-13：按课程目标接入受约束的模型能力

**建议：** 先完成结构化分析计划和指标契约，再让模型负责问题理解、条件澄清和有证据的文字组织；数值继续由可信计算层生成。加入模型、提示词和计划版本、超时、用量与预算记录。各角色具有实际输入输出职责，并用冻结评估集验证。

**验收：** 模型不能改变门店权限；不支持的指标不能补造结果；每个结论能够引用证据；服务失败能够明确终止或切回已声明的规则能力。

### OPT-14：按实际部署需求补齐运维与扩展

当前仅本机运行。多人或远程使用前安排登录限流、账号禁用与重置、HTTPS、数据库备份恢复、迁移版本、日志和健康检查，并验证多进程任务一致性。当前目录未被识别为 Git 仓库，如尚未建立版本管理，应补充代码历史与回退流程。

业务扩展优先考虑 Excel 导入、可分享的 PDF 报告和逐条建议跟进；建议可记录负责人、到期时间、行动及复核指标。库存、成本、客流和活动数据接入后，再考虑毛利、库存、预测和因果分析。

## 7. 推荐开发顺序

| 批次 | 工作 | 完成标准 |
| --- | --- | --- |
| 第一批 | OPT-01～04：指标、同比与范围、读取权限、历史指标版本 | 修复正确性问题并补回归用例 |
| 第二批 | OPT-05～06、08～11：输入、重复检测、评估、类型、体验和文档 | 常见失败可修正，业务可重复验收 |
| 第三批 | OPT-07、12：真实任务阶段、分页、规模测量与必要的存储调整 | 任务状态可信，有性能实测证据 |
| 按目标推进 | OPT-13～14：模型协作、远程使用和业务扩展 | 课程评估或实际部署条件满足 |

如果课程近期必须验收多智能体能力，在第一批正确性修复后将 OPT-13 提前，并同步执行 OPT-08 的评估。若目标是本地业务使用，则优先完成可靠导入、使用体验和备份恢复。
